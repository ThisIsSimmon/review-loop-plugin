# Write Review Request

今のセッションで行った実装・修正を、文脈を持たない別のLLM（レビュアー）に引き継ぐためのレビュー依頼書を生成する。レビュアーはdiffと依頼書だけを頼りにレビューするため、「diffを読むだけではわからないこと」を言語化するのがこのスキルの目的。

## 前提

レビュアーは同じリポジトリの対象差分を読む。特定のレビュー依頼スキルの使用や再委譲を前提にしない。
既存テンプレートとの互換性のため DESCRIPTION / PLAN_OR_REQUIREMENTS / BASE_SHA / HEAD_SHA のラベルは残すが、未コミットの変更を SHA の範囲へ無理に当てはめない。

## Workflow

### Step 1: レビュー対象を実測で確定する

セッション文脈から今回の作業内容（依頼の経緯・要件・設計判断）を整理する。ただし変更の現物はセッションの記憶ではなくgitで実測する:

```bash
git status
git log --oneline -10
git diff --stat   # 未コミット変更がある場合
git diff --name-status <BASE_SHA> <HEAD_SHA>   # コミット済み範囲の変更ファイル一覧
git ls-files --others --exclude-standard   # 未追跡ファイルの確認
```

- 今回の作業がすべてコミット済み → BASE_SHA（作業開始直前のコミット）と HEAD_SHA を確定する。1セッションに複数の作業が混在している場合は、今回レビューを依頼する作業の直前コミットを起点にする。
- 未コミットの変更が残っている → working treeレビューであることを明記し、対象ファイル一覧と、レビュアーが差分を見るためのコマンドを1行添える。案内するコマンドは `git diff HEAD` を基本とする（依頼書を渡す前に対象ファイルがステージされることがあるため。`git diff` はステージ後だと差分が出ず、新規追加ファイルはステージして初めてdiffに現れる）。
- staged のみを対象とする依頼では `git diff --cached` を案内する。未追跡の対象ファイルは、ステージ前には `git diff HEAD` に現れないことと実ファイルのパスを併記する。レビュアーにはレビュー開始時点の状態を確認するよう伝える。依頼書作成のためにステージ・コミットはしない。
- review-loop から `--out` 付きで呼ばれた場合も対象の確定は同じ。差分の範囲は review-loop の script がスナップショットで固定してレビュアーに渡すので、依頼書の確認コマンドは参考として `git diff HEAD` を書けばよく、ステージは不要。
- セッションの記憶とgitの実測が食い違う場合（想定外のファイルが変更されている等）は実測を優先し、差異を依頼書に注記する。
- 今回のセッションに対象となる実装作業が見つからない場合は、推測で書かずに「どの変更についての依頼書か」を1問だけ確認する。

### Step 2: 依頼書を書く

以下のテンプレートで、diffを読むだけではわからないことを簡潔に書く。変更の規模に応じた長さとし、行数を満たすために説明を足さない。

```markdown
# レビュー依頼: <一言タイトル>

## 変更概要（DESCRIPTION）

<何を作った/変えたか。2〜4行>

## 経緯・要件（PLAN_OR_REQUIREMENTS）

<なぜこの変更をしたか。元の依頼内容と満たすべき要件。参照したプラン・ドキュメントがあればリポジトリ内パスで示す>

## レビュー対象（BASE_SHA / HEAD_SHA）

- 対象状態: <commit範囲 / staged / working tree>
- BASE_SHA: <sha> / HEAD_SHA: <sha>（未コミットの場合はその旨と差分確認コマンド）
- 変更ファイル: <一覧（git実測）>
- 未追跡ファイル: <対象に含むもののパス、またはなし>

## diffから読み取れない意図・設計判断

<この依頼書の核。以下の観点で該当するものだけを列挙する>
- なぜこの実装方針を採ったか（検討して見送った代替案があればそれも）
- 一見冗長・不自然に見えるが意図的な箇所
- 既存コード・運用・仕様との整合のために従った制約

## 検証状況

- 実施済み: <実行したテスト・実測での確認内容>
- 未確認: <確認していないこと>

## 特に見てほしい点

<自信のない箇所・判断に迷った箇所・議論してほしい点>
```

- スキル実行時に `--out` 以外の引数（補足指示）が渡された場合は「特に見てほしい点」など該当する節へ反映する。
- 検証状況では、実測・テストで確認したことと未確認のことを混ぜない。未確認の事項を「問題なし」と書かない。書くことがない節は無理に埋めず「なし」と書く（未確認だけは省略せず必ず書く）。
- 内容は日本語で書く。

### Step 3: 出力する

- `--out <path>` が無い場合: 依頼書全文をコードブロックでチャットに出力する（コピペ用）。Markdownファイルや出力用ディレクトリは作成・保存しない。
- `--out <path>` がある場合: そのパスへ依頼書をファイルとして書き、チャットには保存先と変更概要の1〜2行だけを出す（全文は繰り返さない）。保存先は `.tmp/` 配下か、既に存在するディレクトリの中に限る。review-loop では `.tmp/review-loop/<Run ID>/1.request.md` が渡される。

## 完了条件と範囲

- 要件・対象差分・diffから読めない意図・検証済みと未確認を含む依頼書を、コードブロックでチャットに出力したか、`--out` のパスへ書いたら完了する。
- このスキルの作業範囲は依頼書の生成と出力。実装・修正・コミット・レビュー自体は含まない。依頼書に書く事実の裏取りは、`git show` 等の読み取り専用の確認に限る。
- 依頼書に書く経緯・意図は、今回のセッションで実際にあった依頼・判断に限る。それらしい理由を創作して補完しない。
